1. Purpose and scope

The application is a tool to run incident response (IR) tabletop exercises. A live moderator controls each exercise. Participants use the incident response plan of their organization to make decisions.

1.1 Goals

  1. Open source and self-hosted. The organization installs the application on its own server with Docker. The application does not send data outside the organization.

  2. Interactive with a live moderator. The moderator prepares the exercise before the session. During the session, the moderator controls the events and replies to unexpected decisions.

  3. Use of the IR plan. The application makes participants find and cite the sections of their IR plan. It records where the plan helps and where the plan has gaps.

1.2 In scope

  • Scenario authoring, review and storage.

  • IR plan import and plan citations.

  • Live sessions for in-room and remote participants.

  • Logs, scoring, after-action report (AAR) and evidence export.

  • Optional AI assistance for the moderator.

1.3 Out of scope

  • Management of real incidents. The application is for exercises only.

  • Technical simulation (cyber ranges, live attack tools or virtual machines).

  • A hosted multi-tenant service. The project gives a self-hosted product only.

2. Design principles

All design decisions must agree with these five principles.

  1. The moderator controls the exercise. Only the moderator releases injects and changes the story. The AI gives suggestions to the moderator only. Participants never see AI text before the moderator approves it.

  2. The application works without AI. Each function has a manual method. AI makes some tasks faster, but no function needs it.

  3. The IR plan is the center of the exercise. Each inject has expected plan sections. Each response can cite plan sections. The report shows plan use and plan gaps.

  4. The data is sensitive. IR plans and exercise records help an attacker. The application keeps all data on the server of the organization. It has no telemetry.

  5. The evidence is accurate. The logs record real people, real time and simulated time. The score shows actual performance. The moderator must give a reason for each manual change to a score.

3. Users and roles

The application has five application roles. An application role sets the permissions of a user. A plan role is different. A plan role is the IR role that a participant plays in the exercise, for example CISO or CEO.

Rules:

  • One user can have more than one application role in different exercises.

  • The moderator assigns one or more plan roles to each participant before the session.

  • The log records the user account and the plan role for each entry.

  • A participant can join with a session code. The moderator decides if guest access is permitted.

  • The administrator cannot see session content unless the administrator is also the moderator. This rule keeps exercise records private.

4. Exercise process

Each exercise has five phases: Prepare, Brief, Play, Debrief and Report. The corrective actions from the report go back into the IR plan and the next exercise.

The Play phase repeats until the scenario is complete. The Report phase starts the next cycle.

4.1 Prepare (before the session)

  1. The moderator selects the organization profile and its current IR plan.

  2. The moderator selects a scenario from the library or writes a new scenario.

  3. The application replaces the placeholders in the scenario with data from the IR plan.

  4. The application does a consistency check on the scenario facts. The moderator corrects all errors.

  5. The moderator examines each inject, its expected plan sections and its branches.

  6. The moderator adds the participants and assigns their plan roles.

  7. The moderator sets the session date and sends the session code.

4.2 Brief (start of the session)

  1. The moderator starts the session. The real-time clock starts.

  2. The application shows the background story, the systems in scope and the rules of the exercise.

  3. Each participant confirms the plan role on the screen.

  4. The moderator starts the simulated clock.

4.3 Play (main part of the session)

  1. The moderator releases an inject. Participants see the inject and its artifacts.

  2. Participants discuss the inject and submit responses. Each response can cite plan sections.

  3. The moderator sees all responses and citations immediately.

  4. The moderator selects the next step:

    • Release the next prepared inject.

    • Select a prepared branch.

    • Write a new inject for an unexpected response.

    • Put a topic in the parking lot for the debrief.

  5. The scribe records decisions, communications and validation steps in the logs.

  6. The moderator repeats steps 1 to 5 until the scenario is complete.

4.4 Debrief (end of the session)

  1. The moderator stops the simulated clock.

  2. The group discusses strengths, gaps and plan gaps.

  3. The group discusses each item in the parking lot.

  4. The moderator records each finding. Each corrective action gets an owner and a due date.

4.5 Report (after the session)

  1. The application makes a draft AAR from the logs, responses and findings.

  2. The moderator edits and approves the AAR.

  3. The application locks the approved records. Changes after this point make a new version.

  4. The moderator exports the AAR and the evidence package.

  5. The organization tracks the corrective actions. It updates the IR plan and its POA&M.

5. Organization profile and IR plan

The organization profile holds the IR plan and the data that the application extracts from it. Scenarios use this data, so one scenario works for many organizations.

5.1 IR plan import

  1. The moderator uploads the IR plan as PDF, DOCX or Markdown.

  2. The application extracts the text and divides it into sections by heading number. Example: "5.2 Incident Categorization and Severity Level Table".

  3. The moderator examines the section list and corrects errors.

  4. The application stores each section with its number, title, page and text.

  5. The application keeps each plan version. An exercise always links to the plan version that it used.

5.2 Extracted profile data

The application tries to extract the data below. Without AI, it uses text patterns. With AI, it uses the AI provider. The moderator must confirm all extracted data.

DataExampleUse in the exercise
Plan roles and contactsCISO, CEO, MSP contactPlaceholders in injects; role assignment
Severity schemeLow / Medium / High per incident typeThe severity choices that participants see
Response timesPhishing, Medium: 14 business daysScoring of time-based decisions
Incident typesInsider threat, system outage, phishingScenario selection and tags
Reporting channelsSecure email to the security mailboxExpected communication steps
External authoritiesDoD Cyber Crime Center (DC3), 72 hoursExpected notification decisions
Form namesIncident Response Checklist, Communication LogNames of the exported documents

5.3 Plan citations

  • Each response has a Cite plan control. The participant searches the plan and selects one or more sections.

  • The search uses Postgres full-text search. With AI, the application also suggests sections.

  • A participant can mark a response as No plan coverage. The application then makes a plan gap finding.

  • The moderator can add, remove or correct citations during the session.

5.4 Plan coverage

The application compares the expected sections of each inject with the cited sections. It shows the result in four groups:

  • Used: expected and cited.

  • Missed: expected but not cited.

  • Extra: cited but not expected.

  • Gap: no section applies to the response.

6. Scenario format

A scenario is one YAML file. Users can keep scenarios in Git and share them with the community. The application imports and exports this format without data loss.

6.1 Parts of a scenario

PartContents
metaID, title, version, author, license, duration, difficulty, tags (MITRE ATT&CK, NIST SP 800-61 phases)
objectivesWhat the exercise must test
factsThe single source of truth: systems, people, times and root cause
briefingThe background story that participants see at the start
injectsThe events, in order, with artifacts, expected plan sections and branches
rubricThe scoring items for each inject

6.2 Facts and placeholders

  • The facts block holds each fact one time only. Example: the source system, the target system and the start time.

  • Injects and artifacts refer to facts with {{facts.name}}. They do not repeat the value.

  • Injects refer to the organization with {{org.name}}. Example: {{org.role.ciso.name}}, {{org.channel.report}}, {{org.severity.medium}}.

  • The application replaces all placeholders when the moderator prepares the exercise.

6.3 Consistency check

The application must do these checks before the moderator can start a session:

  1. Each placeholder has a value.

  2. Each inject time is after the time of the inject before it.

  3. Each branch goes to an inject that exists.

  4. Each expected plan reference uses a plan concept that the profile contains (for example severity_table).

  5. No artifact has a fixed value that is different from a fact. Example: an IP address or a system name.

6.4 Example

meta:
  id: phish-to-mailbox-rule
  title: Phishing leads to a malicious mailbox rule
  version: 1.0.0
  duration_minutes: 60
  tags: [T1566, T1114.003, nist:detection, nist:containment]
facts:
  victim_user: "Finance analyst"
  victim_mailbox: "{{org.domain.example_user}}"
  phish_time: "09:05"
  rule_found_time: "10:40"
  cui_involved: unknown
briefing: >
  It is a normal Tuesday. The finance team prepares month-end reports.
injects:
  - id: inj-1
    at: "{{facts.rule_found_time}}"
    title: Help desk reports a strange mailbox rule
    audience: [all]
    body: >
      The help desk finds a rule on the mailbox of the {{facts.victim_user}}.
      The rule forwards all mail to an external address.
    artifacts:
      - type: email
        file: artifacts/helpdesk-ticket.md
    expected_plan: [reporting_procedure, severity_table]
    questions:
      - Who do you tell first, and how?
      - What severity do you assign? Use the plan.
    branches:
      - when: "Team disables the account"
        goto: inj-2a
      - when: "Team monitors before action"
        goto: inj-2b
rubric:
  inj-1:
    - item: Report sent through {{org.channel.report}}
      points: 2
    - item: Severity matches the plan table
      points: 2

7. Screens

The moderator console is the most important screen. It must show all live data on one screen without page changes.

7.1 Moderator console

AreaContents
HeaderScenario title, real clock, simulated clock, session status, controls to pause and end
TimelineAll injects in order. Released, current and next injects have different marks.
Current injectInject text, artifacts, questions and expected plan sections
Response feedLive responses with participant name, plan role and citations
Coverage panelUsed, missed and gap counts for the current inject
Next step panelRelease next inject, select a branch, write a new inject, add to parking lot
Notes and logsModerator notes and quick log entries
AI panel (optional)Suggestions that only the moderator sees. Each has Use, Edit and Reject controls.

7.2 Participant view

  • The background story and all released injects, newest first.

  • The artifacts of each inject. Participants can open each artifact in a large view.

  • A response form with a Cite plan control and a No plan coverage control.

  • A read-only IR plan viewer with search.

  • The plan role of the participant, always visible.

7.3 Scribe view

  • The participant view, plus forms for the three logs: communication, action and validation.

  • Each log form fills the real time and the simulated time automatically.

7.4 Observer view

  • The participant view in read-only mode.

7.5 Shared display

  • A large-screen view for in-room sessions. It shows the current inject, the artifacts and the simulated clock.

  • It never shows moderator notes, AI suggestions or the rubric.

7.6 Setup and report screens

  • Organization profile and IR plan import.

  • Scenario library, scenario editor and consistency check results.

  • Exercise setup: participants, plan roles, date and session code.

  • Report editor: AAR, findings and corrective actions.

  • Export screen: AAR, logs and evidence package.

7.7 Design rules

  • The interface must meet WCAG 2.2 level AA.

  • The interface must have a light theme and a dark theme.

  • The participant view must work on a phone with a screen width of 360 px.

  • Color must not be the only way to show a status. Each status also has a text label.

8. Logs, scoring and reports

The logs, the score and the AAR must agree with each other. The application makes all three from the same session records.

8.1 Two clocks

  • Each record has a real time and a simulated time.

  • The real time comes from the server. Users cannot change it.

  • The simulated time comes from the scenario clock. The moderator can move it forward.

  • Reports show both times and label them clearly. Example: "Simulated 09:47 (real 14:12, 3 Feb 2026)".

8.2 Logs

LogFields
Communication logTimes, type (internal or external), from, to, summary, recorded by
Action logTimes, IR phase, action, reason, performed by (plan role), affected systems, result, status
Validation logTimes, validation type, system, method, result, performed by, notes

  • The application records responses, citations and inject releases automatically.

  • The scribe or the moderator adds other entries.

  • Each entry records the user account that made it.

8.3 Scoring

  1. Each inject has rubric items with points. The moderator marks each item as met, partly met or not met.

  2. The score of each IR phase is the sum of its rubric items.

  3. Missing documentation checkpoints reduce the score. A score of 100% is not possible with a missing checkpoint.

  4. The moderator can change a score. The moderator must write a reason. The report shows the change and the reason.

  5. An effectiveness rating needs a short justification. The application does not accept a rating without one.

8.4 After-action report (AAR)

The AAR has these sections:

  1. Exercise information: title, date, scenario version, plan version, participants and plan roles.

  2. Scenario summary.

  3. Phase review: one paragraph and a score for each IR phase.

  4. Plan coverage: used, missed, extra and gap sections.

  5. Strengths and weaknesses.

  6. Corrective actions: control or process, action, owner, due date, documents to update.

  7. Closure: approval name, approval date and final score.

8.5 Evidence export

  • The export is one ZIP file. It contains the AAR as PDF, the three logs as PDF and CSV, and the scenario file.

  • The export has a manifest with a SHA-256 hash of each file.

  • The moderator can map the export to a framework. The first version supports NIST SP 800-171 (CMMC Level 2) 3.6.1, 3.6.2 and 3.6.3.

  • The mapping file is data, not code. The community can add mappings, for example NIST CSF 2.0 or ISO/IEC 27001.

9. AI assistance (optional)

AI is off by default. The administrator turns it on and selects a provider. The application must work fully with AI off.

9.1 Providers

The application uses one provider interface. The first version supports three provider types:

Provider typeData leaves the server?Notes
Local model (Ollama)NoOptional Docker service. Best for sensitive or air-gapped sites.
OpenAI-compatible endpointYes, to the endpointCovers many hosted and local servers
Anthropic APIYes, to AnthropicUses the Claude models

The settings screen must show a warning when the provider sends data outside the server.

9.2 Functions

FunctionWith AIWithout AI
Plan section extractionAI finds roles, severity and contactsText patterns; the moderator corrects
Plan searchMeaning-based search (pgvector)Postgres full-text search
Scenario draftAI writes a draft from a threat and the profileThe moderator writes it or uses the library
Moderator suggestionsPossible results, follow-up questions and new injectsThe moderator decides alone
AAR draftAI writes the narrative sectionsTemplate with the logs filled in

9.3 Rules

  1. AI output goes to the moderator only.

  2. The moderator must approve AI text before participants see it.

  3. The application labels all approved AI text as "AI-assisted" in the records.

  4. The application sends the minimum data for each request. It never sends user passwords or keys.

  5. The application logs each AI request: time, function, provider and size. It does not log the content unless the administrator turns this on.

  6. If the AI provider fails, the application shows an error and continues without AI.

Rules:

  • inject_releases stores the inject text exactly as participants saw it. A later scenario edit does not change the record.

  • audit_events and locked records are append-only. A database trigger stops updates and deletes.

  • Each audit event stores the hash of the event before it. This makes a hash chain that shows changes.

11. Architecture and deployment

The application is one Laravel code base in one Docker image. Docker Compose runs that image in three roles, with PostgreSQL and optional services.

The browsers connect to two services only: app and reverb. All data stays inside the Compose host.

11.3 Portability requirements

  1. All settings come from environment variables. The project gives a .env.example file.

  2. All persistent data is in two named volumes: pgdata and storage.

  3. The image must build for linux/amd64 and linux/arm64.

  4. The image contains all front-end assets. The application loads nothing from a CDN.

  5. At start, the entrypoint runs the database migrations. On the first start, it makes the first administrator.

  6. Each service has a health check.

  7. The command php artisan tabletop:backup makes one archive of the database and the files.

  8. The command php artisan tabletop:restore restores that archive on a new server.

11.4 Install procedure (target)

  1. Copy .env.example to .env.

  2. Set APP_URL and the database password in .env.

  3. Run docker compose up -d.

  4. Open APP_URL in a browser.

  5. Log in with the first administrator account. Change the password.

12. Security and privacy

The application stores data that can help an attacker. It must meet these requirements in the first version.

IDRequirement
SEC-01The application must check permissions on the server for each request. It uses Laravel policies.
SEC-02Passwords must use Argon2id or bcrypt. The application must support OIDC single sign-on.
SEC-03The application must support multi-factor authentication (TOTP) for local accounts.
SEC-04The application must encrypt IR plan files, contacts and session content at rest. The key is APP_KEY, which the organization controls.
SEC-05Guest session codes must have at least 8 random characters. They must expire when the session ends.
SEC-06The application must keep an append-only audit log with a hash chain (see section 10).
SEC-07The administrator must set a retention period. The application deletes old exercise data when the period ends.
SEC-08The application must send no telemetry. It must make no outbound connection unless a remote AI provider is set.
SEC-09Uploaded files must have a size limit and a type check. The application must not run uploaded files.
SEC-10Containers must run as a non-root user. The root file system must be read-only where possible.
SEC-11The application must use TLS. FrankenPHP gives automatic certificates, or a reverse proxy gives TLS.
SEC-12The project must publish a security policy (SECURITY.md) with a private report address.
SEC-13The build must scan dependencies and the image for known vulnerabilities.
SEC-14Sample data in the repository must be fictional. It must not contain real names, contacts or tenant data.
